# Mouse as a first-class input Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every visible control in the overlay works with the mouse, the row under the mouse becomes the selection, and everything clickable reacts to hover.

**Architecture:** New mouse entry points on the pure `OverlayNavigator` (hover, tab click, picker arrows, slider level, media buttons, footer hints), self-tested; an absolute `SetVolume` on the audio view for the volume bar; WPF hover visuals and hit areas in `OverlayWindow`.

**Tech Stack:** C# / .NET 10, WPF, dependency-free self-test.

**Spec (agreed in chat, 2026-11-04):** hover moves the selection (Steam Big Picture style) but only on real mouse movement; pad/keyboard input takes the selection back until the mouse moves again; moving to another row disarms a pending confirm. Clicks: tabs, picker ‹ ›, segmented options (confirm still needs a second click), toggles, volume bar (jump + drag), media ⏮ ⏯ ⏭, footer hints act as their key; right-click = back. Hover: brighter background on the element under the mouse, hand cursor on clickables. Wheel over the volume bar changes volume; elsewhere unchanged (Settings/Info move the selection, Controls nothing).

## Global Constraints

- Navigator rules from earlier stages stay: it never runs item callbacks itself (side effects return as `NavResult`); a held Reorder row ignores mouse input except clicks that would cancel it are ignored too (no accidental drop).
- A double-click (ClickCount > 1) never activates (stage 2 rule).
- Text via `Loc.T`; no keys in XAML. Self-test `All N checks passed.`; build 0 warnings. Never run the app, send input, or touch the PC's audio. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Overlay opens under a still cursor:** the selection stays on the first row (no hover jump). Owned by Task 3 (window ignores MouseMove without a position change since Show).
2. **Mouse drifting across Power while "Confirm?" is armed:** moving to another row disarms; returning does not re-arm. Test in Task 1.
3. **Pad pressed while the cursor rests on a row:** the selection follows the pad; the next pad press is not undone by a stray hover event. Task 3 (hover only on position change).
4. **Volume bar drag beyond its ends:** clamps to 0 and to the device cap. Test in Task 2.
5. **Clicking a tab while on Settings/Info or while holding a Reorder row:** from a page it returns to Tabs on that tab; while holding it does nothing. Test in Task 1.

### Task 1: Navigator mouse entry points

**Files:** `src/OverlayUtils.Core/Overlay/OverlayNavigator.cs`, `OverlayItem.cs`; test `tests/OverlayUtils.SelfTest/Program.cs`

**Produces:**
- `public bool Hover(int index)` — selects a selectable row (clears pending if the row differs); false if unchanged, non-selectable, or holding.
- `public NavResult ClickTab(int visibleIndex)` — Tabs page: switch to that tab (first selectable row); Settings/Info/Sub: return to Tabs on that tab (running any page cancel as `RunHere` if a hold existed — none can exist off Tabs today); holding: `None`.
- `public NavResult ClickStep(int index, int direction)` — select the row, then as Left/Right.
- `public NavResult ClickLevel(int index, double fraction)` — Slider rows with `SetLevel`: select, `RunHere(() => SetLevel(clamp(fraction, 0, 1)))`.
- `public NavResult ClickMedia(int index, int button)` — Media row: −1 Previous, 0 PlayPause, +1 Next.
- `FooterHint` gains `OverlayCommand? Command` (set in `Footer()`: Enter/A → A, Esc/B → B, F2/Back → Settings, ← → → none).
- `OverlayItem` gains `Action<double>? SetLevel`.

- [ ] **Step 1: Failing checks:** Hover moves selection and returns true, same row false, non-selectable false; Hover off an armed Power row disarms it and hovering back does not re-arm (A then only arms); ClickTab on Tabs switches tab; ClickTab from Settings returns to Tabs on that tab; ClickTab while holding → `None` and `Holding` still true; ClickStep(i, +1) on a Choice calls `Step(+1)`; ClickLevel(i, 1.4) calls `SetLevel(1.0)`, (i, −0.2) → `SetLevel(0.0)`; ClickMedia −1/0/+1 call Previous/PlayPause/Next; `Footer()` hints carry the expected commands for keyboard and pad variants.

### Task 3: Window hover, hit areas, cursor, wheel

**Files:** `src/OverlayUtils.App/Overlay/OverlayWindow.xaml(.cs)`, `OverlayViewModel.cs`, `OverlayController.cs`

- Hover: `MouseMove` on a row calls `Hover(index)` only when the cursor's screen position differs from the last one seen (the controller resets the last position on Show to the current cursor position, so opening under a still cursor does nothing); re-render if it returned true. Keyboard and pad commands do not reset it.
- Visual states (XAML triggers on `IsMouseOver`, styled like the stage 2 theme): rows get a subtle surface tint distinct from the accent selection; segmented options, picker arrows, toggle, media buttons, tabs, gear, back chevron and footer hints get a brighter background or text; `Cursor="Hand"` on all of them.
- Clicks (left button, ignore `ClickCount > 1`): tab header → `ClickTab`; picker ‹/› → `ClickStep`; volume bar → `ClickLevel(index, x / width)` on press and while dragging with the mouse captured (release ends it); media ⏮ ⏯ ⏭ → `ClickMedia`; footer hint → `CommandIssued(hint.Command)` when not null; existing row/option/gear/back/right-click behaviour kept.
- Wheel over the volume bar → `ClickStep(index, ±1)` (one notch = one step); elsewhere unchanged.
- Results go through the controller exactly like keyboard commands (same `Apply` path).
